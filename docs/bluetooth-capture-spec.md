# Bluetooth capture page specification

Status: proposed feature. This document does not mean that capture, persistent profiles, or GATT inspection are implemented.

## Purpose

The debug page records bus advertisements and read-only inspection results during a field session. Its output supports later analysis without another visit to the vehicle.

The first target is the Paderborn visit on 24 October 2026. The [protocol explanation](bluetooth-radar.md) provides context. The [field-test checklist](bluetooth-field-test.md) defines the planned checks.

## Existing implementation

Brunel is a native Kotlin app with Jetpack Compose. Relevant existing files are:

- `app/src/main/java/dev/padermodern/companion/PassiveBusScanner.kt`: filtered, balanced-mode scan for BusAccess advertisements. Addresses remain in memory. Unknown packets and simulator records are discarded.
- `app/src/main/java/dev/padermodern/data/BusAdvertisement.kt`: strict parser for protocol 16 and company 4. It returns resolved numeric fields, not a complete raw capture.
- `app/src/main/java/dev/padermodern/companion/BusNameRepository.kt`: name lookup from a downloaded SQLite database in app cache.
- `app/src/main/java/dev/padermodern/companion/TripCompanionService.kt`: existing trip-companion service, not a verified debug recorder.

The debug feature needs a raw observation path before `BusAdvertisement.parse`. Changing the normal trip companion to persist identifiers by default is outside scope.

## Capture modes and boundaries

The default mode is **Capture broadcasts**. It records advertisements delivered by Android without opening a GATT connection.

**Inspect selected bus** is a separate, explicit action for an authorized test vehicle. It connects, discovers services, reads allowlisted data, and disconnects. Read-only connections still use vehicle resources and may affect another client's connection.

An optional **Inspect discovered buses** mode requires an explicit session-level enablement and an authorized target set. Its defaults are one connection at a time, one attempt per observed address per session, and a ten-second connection timeout. Retry is manual.

No mode sends stop, assistance, door-signal, ride, authentication, pairing, or other control commands. No mode calls the three `/busaccess/` action endpoints. No mode writes characteristics or descriptors. Notification subscriptions are excluded because they normally require a descriptor write.

The app does not probe arbitrary nearby phones or wearables. An optional unfiltered scan can identify bus candidates that the current filter misses. Noncandidate payloads stay transient and are not persisted. Unclassified candidates use an explicit **Unknown bus candidate** label and manual retention.

"Every packet" means every relevant scan result Android delivers to this app. It does not mean a complete over-the-air capture. Android can filter, combine, truncate, or omit results. The app cannot record another app's traffic or the backend-to-bus connection.

## Debug-page content

The entry point is **Profil, Debug, Bus capture** in a debug build. Production builds do not enable collection by default.

The session controls are **Start capture**, **Stop capture**, **Add note**, and **Export**. The page shows permission state, Bluetooth state, session duration, received-event count, persisted-event count, dropped-event count, storage use, and last successful flush.

The browser provides two folder-like views:

- **By line**: line, observed bus profile, then that bus's sightings for the selected line.
- **By bus**: observed bus profile, then line and course history with timestamped sightings.

Unresolved values remain under **Unknown line**, **Unknown station**, or **Unknown bus candidate**. Missing lookup text never hides an observation.

A bus detail has **Overview**, **Packets**, **Requests**, **GATT**, and **Notes** sections. The packet list retains duplicates and supports time, protocol, and parse-result filters. An individual packet shows raw bytes, byte length, decoded fields, and the reason for any parse failure.

The request list includes connection attempts, service discovery, allowlisted reads, and this debug feature's lookup downloads. Each request links to its result or timeout. It is not a list of all traffic generated by the phone.

## Raw advertisement record

Each received bus-candidate result is queued for persistence before parsing. Each record contains the following fields when Android exposes them:

- UTC receive time, monotonic receive time, scan timestamp, session ID, and sequence number.
- Observed Bluetooth address, address type if available, device name if available, and RSSI.
- Full app-visible scan-record bytes as hex, byte length, and a payload hash.
- Advertised service UUIDs, service-data entries, and all manufacturer-data entries with their keys and bytes.
- Connectable state, legacy state, PHY values, advertising SID, transmit power, and data-completeness status where supported.
- Candidate-classification reason, parser version, parse result, and parse-error details.
- Protocol, company ID, hardware ID, line ID, destination ID, next-stop ID, course, service flags, and unknown bytes.
- Resolved line, destination, and stop text, plus the lookup database's hash and version when available.

Unavailable fields are null with a reason where useful. Unknown is different from zero. Raw bytes remain unchanged when a later parser produces a different interpretation.

Repeated advertisements remain separate events. UI summaries may collapse duplicates, but export does not silently deduplicate the event log.

Simulator advertisements remain available in explicitly labeled test sessions. They never count as proof of a real vehicle sighting.

## Bus profiles and identity

Every profile has a generated internal ID. Observed Bluetooth addresses, protocol and company values, hardware IDs, and sightings are evidence attached to that ID.

A line is not a permanent vehicle identity. The same bus can change line, direction, destination, course, and next stop. One line can contain several buses at once.

A Bluetooth address is an observed identifier, not proof of permanent identity. A hardware ID can identify a module rather than the whole bus. Reused IDs, address changes, and multiple modules can create ambiguity.

The initial profile key is the session ID and observed Bluetooth address. Matching protocol, company, and hardware IDs can suggest a relationship across addresses or sessions. Such matches remain tentative until reviewed. Line and station matches alone never merge profiles.

A profile retains first and last sightings, address history, raw and resolved field history, packet counts, RSSI range, connection history, discovered services, read values, and manual notes. Collisions remain visible. Manual merges retain their original profile IDs and audit events.

Folder views are indexes over sightings. They do not duplicate or move the source events when a bus changes line.

## Connection and read records

Every active operation has an operation ID, target profile, observed Bluetooth address, start and finish timestamps, and a parent operation ID when relevant.

Connection events retain the requested mode, immediate API result where available, callback status code, connection-state transitions, timeout, exception, disconnect reason, and cleanup result.

Service discovery retains every reported service, characteristic, and descriptor UUID, including characteristic properties and instance identifiers where available.

Reads retain the service and characteristic identifiers, raw returned bytes, byte length, callback status, decoded value, and decode error. A discovery result never implies that a read succeeded.

The initial read allowlist contains vehicle-data characteristic `00002020-0000-1000-8000-00805f9b34fb`, when present and readable. Additional reads require an explicit allowlist change. A readable property alone does not prove that reading an unknown characteristic has no side effects.

Authentication requirements and pairing prompts are recorded as blocked inspection results. The recorder does not bypass authentication or continue into a challenge-response exchange.

Each attempt closes its GATT client on completion, failure, cancellation, or timeout. Stop capture cancels pending inspection and closes connections. The recorder does not retry in a tight loop.

## Network records

Only requests issued by the debug feature are included. Each event records the method, sanitized URL, operation ID, start and finish time, HTTP status, response length, response hash, and failure details.

The lookup database used for a session is copied into the export once, with its hash and provenance. This preserves name resolution after cache eviction or a later database update.

Authorization headers, cookies, API keys, account tokens, and unrelated app traffic are excluded. No private app key is copied from the original APK.

## Durable log and export

The source of truth is an append-only UTF-8 JSON Lines file. Each complete line is one event. It is readable in a text editor and can be replayed to rebuild the profile indexes.

Every event has `schemaVersion`, `sessionId`, `sequence`, `eventId`, `type`, `timestampUtc`, `elapsedRealtimeNanos`, optional `profileId`, optional `operationId`, and a `data` object.

Event types cover session start and stop, advertisement receipt, parse results, identity observations, connection lifecycle, discovery results, read requests and results, network requests and results, notes, permission changes, scan errors, writer errors, and capture gaps.

The event writer uses a bounded queue and writes off the UI thread. Its target flush interval is one second. Stop and export request an immediate flush. The UI distinguishes received, queued, written, and flushed events.

After a crash, recovery reads complete lines and reports an incomplete final line. A crash can lose unflushed events. Queue overflow increments a visible drop counter and creates a gap event when writing resumes. Disk exhaustion stops collection with a visible error. Neither condition is reported as a complete capture.

Files live in app-private persistent storage, not cache and not Logcat. The proposed session directory is `files/bluetooth-captures/{sessionId}/`. Its proposed files are `events.jsonl`, `session.json`, `profiles.json`, and an optional `lookups/` directory. These paths are a proposed contract, not existing outputs.

`profiles.json` is a derived snapshot. `session.json` records app version, device model, Android version, scan settings, granted permissions, enabled modes, session bounds, file hashes, and completion state. It excludes persistent phone identifiers.

Export offers the plain `events.jsonl` file and a ZIP containing the whole session. Export during capture includes only a consistent flushed prefix and records its cutoff sequence. Capture can continue after that cutoff.

The debug UI requires explicit consent before retaining raw Bluetooth addresses. Exports contain vehicle observations and possibly location notes. They remain local until the user shares them. Automatic uploads and analytics are disabled for capture content.

GPS capture is off by default. An optional location mode records permission state and accuracy. A manually entered station note is labeled as a note, not a station decoded from the bus.

Capture files are excluded from automatic backup. Retention and deletion are explicit user actions. Deletion is not part of export.

## Session lifecycle

The scan belongs to the capture session, not the debug screen's composition. Opening a packet or changing tabs does not stop collection.

Background and locked-screen operation require a suitable Android service and device verification. The existing location service does not establish that those requirements are met. If background capture is unverified, the page states that limitation and the field test keeps the app visible.

The session records Bluetooth changes, permission changes, scan failures, suspension, process restart, and resumed collection as distinct events. Restart creates a new session with a link to the interrupted session.

References: [Android background BLE guidance](https://developer.android.com/develop/connectivity/bluetooth/ble/background) and [GATT discovery and reads](https://developer.android.com/develop/connectivity/bluetooth/ble/transfer-ble-data).

## First field-build acceptance criteria

- Starting and stopping a session creates a nonempty, exportable JSONL file without a backend connection.
- Raw bytes survive a parser failure, an unresolved ID, and an unknown protocol.
- Two devices on the same line remain separate. A line change remains in the same observed-device profile.
- A missing hardware ID does not prevent packet retention or export.
- Every initiated inspection has a recorded result, cancellation, or timeout and closes its GATT client.
- Capture performs no characteristic writes, descriptor writes, or pairing. It never sends passenger-control requests automatically.
- Explicit bus actions use `POST https://service.ivanto.de/busaccess/stopRequest`, `doorsignalRequest`, or `serviceRequest` with a JSON `btMac` field.
- Real actions require a running recording, an advertisement seen within 30 seconds, advertised support, and confirmation of permission for that bus. Further taps in the same bus view send directly.
- Demo actions simulate responses without network access. Real actions have a 10-second timeout and no automatic retries or redirects. Each completed or failed attempt can be repeated manually without a cooldown or attempt limit. Only one request can run at a time.
- The log stores each action's URL, body, HTTP code, response body, and result. Responses are limited to 64 KiB and marked if truncated. Only HTTP success with `status: true` counts as server confirmation, not proof of execution at the vehicle.
- Each request is flushed before transmission. Success and failure results are flushed before another attempt is enabled. Closing or restarting the app does not delete these records. The Downloads mirror receives the same events when enabled. Explicit deletion of sessions or exports can still remove the respective copies.
- A read failure retains the original callback status and does not appear as a successful read.
- The exported lookup snapshot reproduces the session's resolved names without network access.
- A force-stop leaves earlier flushed events readable. Recovery reports any incomplete tail.
- Queue overflow and storage failure produce visible incomplete-capture states.
- The user can export from the physical phone and open the log on another device before the trip.
- Navigating away from the debug screen preserves capture. Locked-screen support is either verified or explicitly marked unsupported.

## Scope after the field test

The first build prioritizes raw capture, durable export, profiles, and failure visibility. Full protocol-18 decoding, sophisticated identity matching, and authorized automatic inspection are separate work if they delay a reliable recording build.

The field capture can establish what packets this phone receives and which authorized reads succeed. It cannot prove fleet-wide compatibility, guaranteed delivery, complete radio capture, or physical execution of passenger-control commands.
